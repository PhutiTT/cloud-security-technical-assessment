# Question 2 - Risk review

Scope: Annexures A-D of the supplied assessment. These are proposed permissions, not an observed deployment. The account IDs and architecture are assessment examples. No IAM or database changes were made.

## 1. SSM automation execution role (Annexures A and B)

The diagram shows a user triggering an Azure DevOps pipeline on an EKS agent pod. The pod assumes a role in each of three target accounts, starts Systems Manager automation, and runs commands on EC2. This crosses two trust boundaries: pipeline to AWS and automation to instance. Approval should be **conditional on a narrower policy, role trust, and tests**.

| Finding and risk | Possible outcome | Recommended control and validation |
| --- | --- | --- |
| **Critical: arbitrary command execution.** `ssm:SendCommand` permits `AWS-RunShellScript` and `AWS-RunPowerShellScript`. The `AutomationAllowed=true` and `Application=Automated-Deployment-Dev` tags select targets, but neither restricts the shell commands, script URL, or package contents. | A compromised pipeline or role runs arbitrary code on every matching EC2 node, potentially as the agent's privileged OS user. | Prefer a version-pinned custom SSM document with constrained parameters and immutable, signed deployment artifacts. Limit the role to approved documents and target tags; use approvals for production, minimum IAM role duration, and concurrency/error limits. Test an unapproved document and target are denied. |
| **High: tag and resource scope bypass.** `ec2:CreateTags` covers all instances in one ARN scope. A principal with this permission can label an instance as eligible for its own `SendCommand` access. `StartInstances`, `StopInstances`, and `RebootInstances` also cover all instances in that scope. | Unauthorized deployment targets, disruption, or outages. | Remove EC2 write actions unless the runbook demonstrably needs them. Delegate target tags to a separate protected provisioning role; if tag updates are necessary, restrict `aws:TagKeys`, `aws:RequestTag`, and existing resource tags, and deny changes to `AutomationAllowed`/`Application`. Test self-tagging and stop/reboot on unrelated instances. |
| **High: account/ARN mismatch.** `EC2ControlledActions` uses an 11-digit account ID; `SSMSendCmdInstances` uses a 12-digit ID, while `customer-*` documents and CloudWatch Logs refer to another account. The role is shown in three target accounts. | Invalid permissions, denied deployments, or access to an unintended shared document/account. | Generate one policy per target account and use its exact 12-digit ID in instance and log ARNs. Confirm whether a document is owned in that account or explicitly shared from the other account. Check policy variables and ARNs with IAM Access Analyzer and a dry run in each account. |
| **High: broad S3 access.** `s3:GetObject` and `s3:PutObject` on `arn:aws:s3:::*/*` permit reading or overwriting any object allowed by other controls. `GetBucketLocation` has a leading space after `:::` and appears malformed. | Exfiltration, artifact tampering, or deployment failure. | Scope to a named deployment bucket and prefix, enforce TLS, encryption and bucket-side access controls, and separate read from write. Correct the bucket ARN and verify whether the *execution role* needs S3 at all. Test other bucket access is denied. |
| **Medium: logging may be missing or mis-scoped.** A CloudWatch Logs ARN in one account is embedded in a role assumed in other accounts; `CreateLogGroup` and `DescribeLogGroups` have different resource support from stream/event actions. | Failed logging or no reliable command output for incident response. | Define log destination and writer principal in each account, create log groups ahead of time, enforce encryption/retention, and grant only the required actions on supported resources. Set Run Command `CloudWatchOutputConfig`; verify a test command produces logs and an audit event. |
| **Medium: broad inventory and deny-list approach.** `ssm:GetDocument`/`ListDocuments` and EC2 describes at `*` expose metadata. The long `DenyHighRiskSSM` list blocks named actions only; other permissions attached later can still allow omitted high-risk actions. It does not constrain shell execution. | Information leakage or permission creep after future role changes. | Use a minimal allow list, review effective permissions across all attached policies, require change review for new permissions, and use a permissions boundary or SCP only where appropriate. Keep read actions needed by the runbook. |
| **High: trust chain not specified.** The diagram labels IRSA, but the exact EKS service account, OIDC subject/audience, pipeline identity, `sts:AssumeRole` trust in each target account, and SSM automation assume-role boundary are absent. The policy has no `ssm:StartAutomationExecution` action despite the diagram. | Any pod or pipeline able to obtain/assume the role could execute deployments, while the intended automation may fail. | Bind IRSA to the exact service account and namespace; constrain target-role trust to the source role, external ID/source identity where applicable, and a dedicated role per environment. Add narrowly scoped `StartAutomationExecution`/`iam:PassRole` only if the specific runbook needs them, with exact resource ARNs. Test the actual end-to-end call chain and reject a different pod. |

The `ssm:SendCommand` document and node permissions are evaluated as separate resources; retaining a tagged node statement alone does not make an unrestricted shell document safe. AWS documents the tag-based pattern and output monitoring: [Run Command setup](https://docs.aws.amazon.com/systems-manager/latest/userguide/run-command-setting-up.html). AWS also documents shared document ARNs for [SendCommand](https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_SendCommand.html).

**Decision:** Do not attach Annexure A as-is. First reconcile account IDs and execution roles, remove broad S3/EC2 privileges, replace generic shell documents, and prove audit logs and negative authorization tests in each target account.

## 2. RDS policies and database roles (Annexures C and D)

The diagram describes SailPoint membership -> Microsoft Entra ID group -> IAM Identity Center permission set -> IAM-authenticated RDS database login -> database role. Annexure C instead grants RDS **control-plane API** access. Those are distinct authorization layers. Approval should be **conditional on replacing these policies with database connection permissions and enforcing SQL privileges inside the database**.

| Finding and risk | Possible outcome | Recommended control and validation |
| --- | --- | --- |
| **Critical: `rds:*` on `*` for Admin and CRUB.** Both can modify/delete instances, snapshots, backups, credentials, encryption settings, and network exposure where APIs permit. CRUB is effectively an RDS administrator, not a read/write SQL user. | Destructive changes, data loss, or exposure beyond the intended database. | Remove `rds:*` from end-user permission sets. Keep infrastructure administration in a separate, time-limited, approved break-glass role with narrowly scoped API rights and monitoring. |
| **High: no `rds-db:connect`.** None of the three policies grants IAM database authentication to a named database user. `rds:Describe*` does not grant SQL `SELECT`. | Intended users cannot authenticate using IAM; application teams may fall back to shared passwords. | Enable IAM DB authentication on a supported engine and grant `rds-db:connect` on exact `arn:aws:rds-db:eu-west-1:<account-id>:dbuser:<DbiResourceId>/<db_user>` ARNs in the appropriate account. For Aurora or RDS Proxy use their corresponding resource IDs. Create matching DB users and SQL roles. |
| **High: DB privilege boundaries are undefined.** IAM auth controls who may connect as which DB user, while the database grants determine `SELECT`, DML, and DDL. Shared DB users hide individual SQL identities. | ReadOnly can write if DB grants are wrong, or Admin rights are inherited unintentionally; weak attribution. | Create distinct DB users or mapped roles for ReadOnly, CRUB, and Admin. Grant ReadOnly `SELECT` on required schemas, CRUB `SELECT/INSERT/UPDATE/DELETE`, and Admin only the required DDL/DML; set default privileges for future objects. Test actual SQL `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, and `DROP` for each role. Prefer named users per person if individual audit attribution is needed. |
| **Medium: federation and lifecycle.** A SailPoint group change must reach Entra ID, IAM Identity Center, the permission set assignment, and the DB user mapping. IAM tokens and active sessions have different lifetimes. | Delayed revocation, stale sessions, or incorrect role assignments. | Test provisioning and deprovisioning end to end, set short sessions where feasible, terminate sessions for urgent revocation, require MFA/conditional access, and review group/permission set assignments periodically. Capture IdP, CloudTrail, connection, and DB audit events. |
| **Medium: network and transport.** IAM permissions alone do not establish a safe network path or encrypted DB session. | Valid credentials used from an unintended route, or connections fail. | Keep the DB private; constrain security groups to approved clients, use TLS and certificate verification, use Secrets Manager only for any remaining passwords, and test from both an authorized and unauthorized network path. |
| **Medium: excess supporting APIs.** The Admin role also grants autoscaling, alarm management, SNS publish, service-linked role creation, `pi:*`, and DevOps Guru access. ReadOnly grants EC2 metadata reads. | Operational changes or metadata exposure unrelated to SQL roles. | Remove them from DB-user permission sets. Grant the few needed control-plane read actions to separate operator roles. Bound `sns:Publish` to a topic and `iam:CreateServiceLinkedRole` to a justified setup workflow if retained. |

Illustrative **connection** policy for one role (replace every placeholder; do not attach unchanged):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ConnectAsReadOnlyDbUser",
    "Effect": "Allow",
    "Action": "rds-db:connect",
    "Resource": "arn:aws:rds-db:eu-west-1:<account-id>:dbuser:<DbiResourceId>/readonly_user"
  }]
}
```

Create separate resources for `crub_user` and `admin_user`, then assign their permission sets to the matching Entra groups. For cross-account access, the connection role and its policy belong in the database account. See AWS [IAM DB authentication policy](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.IAMPolicy.html), [supported authentication methods](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/database-authentication.html), and [database account creation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.DBAccounts.html).

**Decision:** Reject Annexure C as the implementation of the stated DB access tiers. Build three database-auth permission sets and SQL roles, test both API and SQL negative cases, and keep RDS infrastructure administration separate.
